# 主题 07：宏与元编程 Macros & Metaprogramming

> 同一道题：square(7) 和 cube(3)——小题大做地用上各语言的元编程设施，
> 只为看清“谁在什么层面做代码变换”。
> 输出六个语言完全一致。交互展示页：[ui/index.html](ui/index.html)

## 各语言的元编程层次

| 语言 | 设施 | 变换发生在 | 强度 |
|---|---|---|---|
| **C++** | 预处理器宏 `#define` | 编译最早期：纯**文本**替换 | 最原始最危险 |
| **C++（现代）** | 模板 + `constexpr` | 编译期：有类型、可检查 | 图灵完备，正道 |
| **Rust** | `macro_rules!` | 语法分析后：操作 **token 树** | 比文本宏强得多；derive 过程宏更上層 |
| **Python** | 装饰器 / 元类 | **运行期**：函数和类都是对象，可替换 | 灵活，无编译期 |
| **Go** | ❌ 无宏 | 官方只认 `//go:generate` 代码生成 | 刻意反元编程 |
| **TS** | ❌ 无宏 | “元编程”在**类型层**：泛型/映射类型做编译期类型计算 | 类型体操的乐园 |

## 教学要点

1. **C 宏的经典坑**：`#define SQUARE(x) x * x`（没加括号）展开 `SQUARE(a+b)` 变成 `a+b*a+b`——文本替换不懂运算优先级。所以示例里是 `((x) * (x))` 外加双层括号。
2. **Rust 的 `macro_rules!` 解决了文本宏的硬伤**：`$x:expr` 匹配的是语法单元（表达式），天然带括号语义； hygienic（卫生宏）不会意外捕获变量名。
3. **“运行期元编程”的代价**：Python 装饰器每次调用都走包装层；编译期元编程（constexpr/宏）零运行时成本。
4. **Go 的立场**：连三元运算符都拒绝的语言，自然拒绝宏——复杂性预算花在了别处。

## 输出

```
square(7) = 49
cube(3) = 27
```
